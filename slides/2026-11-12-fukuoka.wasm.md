# 🎯やりたかったこと

- Component Model の契約:
    - `borrow` で受け取ったハンドルは、呼び出しが返る前に drop しなければならない
    - [参考](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Explainer.md#fundamental-value-types): "an opaque address of a resource that must be dropped before the current export call returns"
- これを意図的に破り、エラーが起きることを確かめたい

# 🤔なぜエラーにならないのか

- 契約の対象は「**ハンドル**<small>（インスタンスのハンドルテーブル上の整数）</small>」であって、リソースの実体ではない
- `self` は Python コンポーネント自身が実装するリソースの実体 (rep)
- 自分の持ち物への参照を保存するのは、何の違反でもない

# 💁仕様上の根拠: `lower_borrow`

[`component-model/design/mvp/canonical-abi/definitions.py` の `lower_borrow`](https://github.com/WebAssembly/component-model/blob/d095e2f60ddae1f9a1e9b1e2fb547ec1114da677/design/mvp/canonical-abi/definitions.py#L1720-L1726):

```python
def lower_borrow(cx, rep, t):
  if cx.inst is t.rt.impl:
    return rep          # 実装者には rep をそのまま渡す
  h = ResourceHandle(
    t.rt, rep, own = False, borrow_scope = cx.borrow_scope
  )
  h.borrow_scope.num_borrows += 1
  return cx.inst.handles.add(h)
```

# 💁仕様上の根拠: `lower_borrow` （続き）

- リソースを**実装したコンポーネント**に borrow を渡すときは、borrow ハンドルを作らない（最適化）
- `num_borrows` が増えないので、呼び出し終了時の `trap_if(self.num_borrows > 0)` も発火しようがない

# 💁componentize-py の実装も同じ（らしい）

[`componentize-py/runtime/src/lib.rs` の `push_borrow`](https://github.com/bytecodealliance/componentize-py/blob/9ff99dabc05a918a9875bad58b0ecb39cb90bb9a/runtime/src/lib.rs#L1945-L1963)

- **`export` したリソース型**
    - rep を元の Python オブジェクトに戻すだけ
- **import したリソース型**: borrow を記録し、呼び出し後に `release_borrows` で自動的に drop
    - Python オブジェクトの `handle` を `0` にして無効化
- → 高レベルのバインディングを使う限り、利用者のコードからは契約を破れない

# 👿今度こそ契約を破る

コンポーネント自身で実装していないリソースを `borrow<blob>` で受け取るコンポーネントが必要

```wit
interface processor {
  use blobs.{blob};

  process: func(b: borrow<blob>);   // b をグローバル変数に保存
  later: func() -> list<u8>;        // 保存した b を使う
}

world processor-world {
  import blobs;
  export processor;
}
```

# ⚙️構成 2

[こちらのコミット](https://github.com/igrep/wasm-component-example/commit/84e60fc4a052aeb10d9b342594d6df7962a91831)より:

- `blob` の実装<small>（`componentize-py` で作成）</small>:
    - Python コンポーネント (`python.wasm`)
- `processor` の実装<small>（`jco componentize` で作成）</small>:
    - JS コンポーネント (`processor.wasm`)
- ホスト: 引き続き Node.js
    - Python の `Blob` を作り、`processor.process(blob)` に渡す
- `jco transpile --map` で `import` を Python の `export` に繋ぐ

# ⚙️構成 2 （続き）

processor.js:

```js
let escape = null;

export const processor = {
  process(b) {
    escape = b;
    b.append(100);
  },

  later() {
    escape.append(101);
    return escape.getContents();
  },
};
```

# ⚙️構成 2 （続き）

processor-host.js:

```js
import { blobs } from "./out-python/python.js";
import { processor } from "./out-processor/processor.js";

const blob = new blobs.Blob([1, 2, 3]);
processor.process(blob);
console.log(blob.getContents());
console.log("----");
console.log(processor.later()); // ← ここでエラー！
```

# 💥結果: 契約違反を検出できた

```
Uint8Array(4) [ 1, 2, 3, 100 ]      ← process() 中は正常
----
TypeError: Resource error: Not a valid "Blob" resource.
    at Blob.append (out-python/python.js)
    ...
    at _trampoline0 (out-processor/processor.js)
```

- `process()` から返った時点で、componentize-js のバインディングが borrow ハンドルを drop
- `later()` では解放済みのハンドルテーブルのスロットを読み、偽の `Blob` を作ってしまう
- それを Python 側の `python.js` が「有効な Blob ではない」として拒否

# 🚫「borrow が呼び出しより長生き」のトラップは出ない

- `jco transpile` の出力には契約チェックが実装されている
    - `'borrow handles still remain at the end of the call'`
- しかし `componentize-js` がハンドルを自動で `drop` するので、このチェックは発火しない
- 見えるのは先述の「無効なハンドル」のエラー
- このトラップを直接見るには、`resource.drop` を呼ばないコンポーネントを WAT で手書きする必要がある（らしい）

# 📰まとめ

- `borrow` の契約は**他のコンポーネントが実装したリソースのハンドル**に対するもの
    - 自分が実装したリソースの実体を保存するのは合法
- 契約違反のチェックは仕様にも jco にも存在する
- ただし高レベルのバインディング (componentize-py / componentize-js) が自動で drop するため、通常は「無効なハンドル」としてコンポーネント内のエラーとして表面化する
